Found by an independent code-review agent (2026-09-25):
- [x] ClaudeCodeClient.launch()'s 120s timeout didn't actually bound anything: readAll() blocked reading the subprocess's full output *before* waitFor(TIMEOUT_SECONDS,...) was ever reached. Fixed by redirecting output straight to a temp file (ProcessBuilder#redirectOutput) instead of reading it from a pipe - a piped read can block until the process writes/closes, which is exactly what defeated the timeout; a file has no such bounded buffer to block on either side, so waitFor(timeout) now genuinely bounds the wait, and the output is read from disk afterward (fast, since the process already finished). Empirically verified with a fake executable substituted for CLAUDE_EXECUTABLE_PATH: one that hangs forever confirms the fix actually times out at ~120s and throws (not tested against the old broken code - the bug's mechanism was clear enough from reading, this verifies the fix, not the regression), and one that exits normally confirms output/exit code still come through correctly via the file-redirect path.
- [x] NotionExtractor's and DiscordNotifier's HttpClient instances have no connect/request timeout configured - fixed with a 30s `HttpClient.connectTimeout` (bounds the TCP handshake) plus a 30s `HttpRequest.timeout` (bounds the whole wait for a response - the one that actually matters for "server accepts the connection but never responds"). `HttpTimeoutException extends IOException`, so no new exception handling was needed anywhere - it flows through the same `catch (IOException | InterruptedException e)` Main already had. Empirically verified: a throwaway `ServerSocket` that accepts a connection and then never responds caused the request to correctly throw `HttpTimeoutException` at exactly 30s instead of hanging.
- [x] Main's auth-failure branch calls deliver(dryRun, dotenv, alert) before printing the alert to stderr - if deliver() itself throws (e.g. Discord unreachable), the real cause (stale Claude Code login) never gets printed, only a generic top-level "Digest run failed" message. Closed as a side effect of the retry/exit-code-check work below: both failure branches now go through a shared `failWithAlert` helper that prints to stderr first, then attempts delivery.
- [ ] Main's DigestLog.write() runs after the Discord post - if the write fails (disk full, permissions), the whole run reports as failed even though the digest was already delivered; a naive retry would re-post the same digest.
- [ ] NotionExtractor.fetchAllPages (the pagination/cursor-chaining loop) has zero test coverage, despite a package-private constructor (NotionExtractor(String, HttpClient)) existing specifically to allow injecting a fake HttpClient for exactly this.
- [ ] Main.run()'s orchestration is entirely untested, including the specifically-documented "skip DigestLog.write on auth failure" behavior (ARCHITECTURE.md decision #3 / the isLoggedIn item above) - nothing would catch a regression there.
- Already known and deliberately deprioritized, independently reconfirmed by the same review: the raw string-concatenated JSON body in fetchAllPages's pagination request. Still low severity; noting the reconfirmation, not re-opening it as new.

Found during live cron operation on the homelab machine (2026-10-02): the first two real cron-triggered runs hit `Failed to refresh OAuth token: another Claude Code process is refreshing it or exited mid-refresh` once (day 1), then ran clean with no local changes (day 2) - confirmed via `ps -ef` there's no lingering `claude` process on the homelab machine, so a locally-orphaned process isn't the explanation; more likely Claude Code's own background activity or a transient server-side hiccup. Two concrete gaps this exposed in `Main`/`ClaudeCodeClient`, independent of root cause:
- [x] Bounded retry in `ClaudeCodeClient` specifically for this one documented-as-transient error ("retry in a minute" per the error's own text) - not a general retry-on-any-failure policy (that stays against the Behavior rule), a narrow, deliberate exception for this one known-transient condition. Lives in a `launch()`/`launchOnce()` split (retry policy separated from a single invocation) so both `run()` and `isLoggedIn()` benefit with no duplication. Trigger is text-match only (`isRetryableFailure`, pure and tested), not gated on exit code - we never actually confirmed what exit code this error produces, and gating on an unverified assumption risked a retry that silently never fires. Empirically verified end-to-end (not just the pure detection function) via the manual harness's new Run E: a fake executable that fails once with the real, verbatim error text and succeeds on the second call - confirmed the real retry loop waits ~60s and recovers.
- [x] Exit code checking in `Main`: `claude.run(prompt)`'s `ClaudeCodeResult.exitCode()` is now checked before treating `result.output()` as the digest, reusing the same alert-and-bail shape already used for the `isLoggedIn()` failure (extracted into a shared `failWithAlert` helper once there were two call sites, not one). Also folded in while rewriting those exact lines: `failWithAlert` now prints the real cause to stderr *before* attempting delivery, closing the previously-separate "alert lost if deliver() itself throws" item below.

Found during live cron operation on the homelab machine (2026-10-03): the OAuth-refresh error recurred and slipped past the exit-code check entirely. Confirmed via direct evidence, not hypothesis - `cron.log` showed `"Digest complete and posted to Discord."` (the success-path line) for the failing run, and `digest-log.json`'s `"recommendation"` field was the raw OAuth error text. Both are only reachable when `result.exitCode() == 0`, which empirically confirms what was flagged as an open, unverified assumption when the exit-code check was built: `claude -p` can exit `0` even when its entire output is this error. The retry worked as designed (it's bounded, not a guarantee); the exit-code backstop just had nothing to catch because the condition it checked for never occurred.

Reuses `isRetryableFailure` rather than duplicating the error-text match anywhere else. Unit-tested: exit 0 + normal output -> false, exit 0 + the OAuth error text -> true (the exact case that slipped through), exit 1 + unrelated output -> true (preserves prior behavior).
